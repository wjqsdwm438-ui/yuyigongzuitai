# Skill 原子化与运行时依赖

## 定义

原子不是越小越好，而是单一职责下的最小可用能力：职责清楚、能运行、能测试、能观测。把一个工具拆成互相依赖的零件，会增加每次使用的重装成本，反而损害工具价值。

## 三层边界

一个可维护的 Skill 需要区分三层：

1. **核心业务能力**：完成一个明确业务动作，例如查指标、校验 SQL、生成建表语句。
2. **运行前提与依赖**：登录态、权限、数据库连接和上下文。业务 Skill 声明依赖，不重复实现依赖。
3. **编排逻辑**：执行顺序、重试、降级和转人工，由 workflow 或运行时负责。

Skill 的原子化不等于把必要上下文拆散。职责可以单一，但输入、前置条件、组合约束和失败边界必须交接完整。

## 认证与权限

认证、权限检查和 token 刷新属于独立能力维度，但不应复制到每个业务 Skill，也不应让每个 workflow 手工重复声明。推荐由 Skill 声明依赖，由运行时统一注入和维护：

- Skill 声明所需权限，例如 `data:read`。
- 有效 token 直接复用。
- token 过期时自动刷新。
- 无权限时返回明确的权限错误。
- 认证状态由运行时维护，避免重复登录。

## Skill 交接契约

每个 Skill 至少说明：

- 负责什么，以及明确不负责什么；
- 输入和输出格式；
- 权限与其他前置条件；
- 是否修改数据；
- 错误码、超时和取消行为；
- 失败策略：重试、降级或转人工。

## 编排示例

“AI 问数”不是一个 Skill，而是一条生产线：

意图识别 → 指标定义检索 → SQL 生成 → SQL 安全检查 → 查询执行 → 结果校验 → 结果解释。

各环节保持清晰职责；认证不嵌入每个环节，而由运行时向需要权限的环节提供上下文。

## 最小验收场景

至少覆盖：无认证态、有效 token、过期 token、无表权限、指标不存在和查询超时。查询超时必须自行停止，不能无限重试。功能测试与依赖测试分开，但要验证运行时能可靠地把两者接起来。

## 落地顺序

1. 先问 Skill 负责哪一个动作。
2. 把运行前提写成依赖，不藏在业务代码里。
3. 定义输入、输出和错误格式。
4. 补正常、边界和失败样例。
5. 最后放进 workflow 编排。

## 归属边界

本文件是 Agent/Skill 设计参考，不是具体业务规则、世界模型事实或认证实现说明。具体 Skill 的契约写在其 `SKILL.md`；流程顺序写在 workflow 设计中；认证注入和 token 生命周期由运行时实现。
