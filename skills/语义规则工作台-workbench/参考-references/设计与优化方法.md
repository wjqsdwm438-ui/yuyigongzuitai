# Agent / Skill 设计与优化（上游方法的本地适配）

本页把 Sentry `skill-writer`、`prompt-optimizer` 与 Anthropic `skill-creator` 的相应方法接到工作台，不要求安装三套插件。上游原件已按提交固定在仓库 `依赖-dependencies/技能上游-upstream`；它们是方法参考，不授予工具调用、安装或业务权限。工作台的来源、语义保真、项目隔离约定继续适用。

## 1. 先定要改变的行为和修改位置

设计或改稿前，读取 [Sentry 修改前后精确检查](../../../依赖-dependencies/技能上游-upstream/哨兵-sentry-skills/skills/skill-writer/references/authoring-path.md)，按下列本地约定使用，不照搬其中注册和目录规则。

从用户请求和实际文件得到：要完成的结果、已授权改动、保留约束、允许工具与完成证据。只读评估交付候选；已批准本地修改则实际改文件并检查成品。不能因工作台通用实施命令未接通而拒绝已获准的本地维护，也不能把文件工具执行冒充程序自动实施。

先查目标正文、实际调用入口及必要共享定义；区分已读取内容、只出现了路径但未加载的内容、范围外内容。列名或文件名存在，不等于该内容进入 Agent 输入。先找可替换、收窄或删除的旧规则，再决定是否增加指令。

选择最短适用路径：

- **新建**：选能完成任务的最小执行结构，直接交付主指令、必要引用和代表性产物；固定步骤用流程，开放判断用 Agent，没有独立信息/权限需求不拆角色。
- **局部修改**：明确原义到新义的差异，实际更新目标及必要调用关联；无关段落保持原状。
- **反复失败**：先进入第 2 节归因与候选比较，不以整篇重写作为默认答案。

完成条件是得到了具体行为差异及修改落点，不是填齐一张设计表。材料中能自行查证的问题自行查；缺少不可逆动作授权只停该动作，其余可独立工作继续完成。

## 2. 失败归因与候选选择

反复失败时读取 [Sentry 优化循环](../../../依赖-dependencies/技能上游-upstream/哨兵-sentry-skills/skills/prompt-optimizer/references/meta-optimization-loop.md)。本地同名 ECC 技能只优化用户提问，不是这个执行方法，不调用它代替任务。

固定旧版与失败输入，沿实际加载 → 判断 → 工具参数 → 应用结果找第一个可观察偏离。使用工具返回和最终状态，不请求内部思维，不采信“已经成功”作为唯一依据。

| 证据指向 | 首选修改 | 验证落点 |
|---|---|---|
| 规则没加载、路径或版本错误 | 入口、检索或交接 | 实际输入和所有相关调用方 |
| 规则齐全但解释错条件、例外、优先级 | 对应指令或必要示例 | 正常、条件翻转与近似反例 |
| 候选正确但参数、应用或成品错误 | 工具契约或工程实现 | 应用后的文件/状态，不只看提案 |
| 规则冲突或合法的新要求 | 有来源的局部裁决/改稿 | 哪些预期确实获准改变 |
| 证据不足 | 可被推翻的假设与最小探针 | 能取得的证据先主动取得 |

对不明确的指令瓶颈保留两个有实际区别的候选：一个最小修复，另一个针对同一根因改变组织或示例。用同一材料和权限比较，再让较好的候选通过新材料检查。明确的代码故障可直接最小修复；不要为机械凑两个方案写冗余代码。

每轮只动一两个可解释的因素。简记假设、实际改动、观察结果、保留/拒绝理由；没有改善、行为来回摆动、正常路径退化或瓶颈不在指令时，停止继续堆规则，转修对应机制。失败候选不覆盖有效版本，也不删掉它的失败证据。

## 3. 交付实际改稿，不交一份建议清单

修改正文时再使用实际可用的 `writing-for-agents` 组织文档。它负责步骤、指针、信息层级和删重；业务含义由来源与授权约束。修改后重新读完整生效路径，检查新增内容是否让旧限制重复、冲突或失效。

需要保留的对象、条件、量词、例外、义务强度、来源身份和历史版本见核心技能。特别检查：

- 新调用约定是否同步到入口与调用方，而不只是主文档改了。
- 所谓“更安全”的方案是否把正常任务改交人工、缩为少数模板或新增审批；这些是功能与减负退化，不是免费改进。
- 所谓已有接口、白名单或配置是否真的存在；缺失的必要实现自己在获准范围完成，不给用户留下一个虚构依赖。
- 获准修改不等于授权安装、外发、真实业务审批；保存旧版后核对源未变，避免覆盖他人改动。

例：原要求“审核通过且用户明确批准发布后才可发布，用户取消则停止”。可压缩为“仅在审核通过、用户明确批准且未取消时发布”。“审核通过后发布”丢了授权，“每一步都重新批准”新增了义务，均不能当作写作优化。

新建任务交付能处理代表性输入的正文和具体结果；修改任务交付真实文件差异或只读候选。用已有审阅包说明改变、保留及必要关联，不再新建第二份正式规则或强制每次新增 SPEC 文件。

## 4. 检查结果，而不是听候选解释

读取 [Sentry 正反例迭代方法](../../../依赖-dependencies/技能上游-upstream/哨兵-sentry-skills/skills/skill-writer/references/iteration-path.md)；本地以已有审阅附件保存证据，不照搬目录或文件命名。先检查原失败，再检查正常路径、边界与应不同处理的近似情况。

能运行的代码或文件变更，助手在交付前实际运行检查；不能只给出计划。已授权修改文件的任务必须检查文件存在及实际内容，没有改动的空操作也必须会失败。没有相关工具时明确交付层级，不把建议当成实施。

要求证明 Skill 优化效果时，由组织者按 [行为对照与触发验证](regression.md) 运行：旧版和候选在相同初始材料、权限、工具和模型设置下，分别实际完成任务；独立审阅正文与最终工作区，不只检查字段。组织者保留答案，答题者不得读取固定预期或其他运行产物。

旧版与新版均通过表示该样本持平。量表通过却观察到实际缺陷时，缺陷仍阻断采用；保留原评分并改进后续检查，不追溯改分制造提升。留出材料不能在改稿前泄露，用来挑过候选的材料不能再称最终独立测试。

## 5. 按真实状态交付并维护

助手先修掉基本错误，用户只接收必须作业务取舍或授权的差异。没有这种未决项时继续完成，不重复问是否开工。

按“已改文件 / 已验证场景 / 仍未验证”报告，附实际产物和恢复点。候选含义检查、行为检查与业务批准分开；出现源变化或验证失败时停止覆盖，保留当前有效版本。

记录本次生效范围与失效条件：规则或工具版本变化后重新判定复用，历史事实不覆盖。治理收益看实际返工、用户补充推动、审核/回查与记录维护成本；没有观测不编造收益或总分。
