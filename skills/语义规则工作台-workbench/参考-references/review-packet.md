# 一次只审需要重新判断的含义

这是交付格式参考，不是要求填满的表单，也不是第二份正式正文库。

## 核心页面

**本次结论：**建议做什么；事实、判断和未证实假设分别说明。

| 目标规则／设计项 | 原义与依据 | 本次拟改 | 必须保持 | 影响与待核查 |
|---|---|---|---|---|
| 沿用原 ID；没有时先定位 | 回指实际材料，不只引用上轮摘要 | 明示实质差异；只润色也明确说明 | 只列与本次改动有关的边界 | 带必要定义、例外和引用，不把所有规则都塞进来 |

**验证证据：**列相关场景的预期与实际观察，未执行写未执行。若预期也改变，标明是用户已决定的新行为，还是仍待确认的建议。

**需要你判断：**一个或少量具体取舍，避免“是否满意”“是否继续”式重复确认。无需新决策且已有授权时，直接交付授权范围内的结果。

## 记录价值的边界

- 来源记录回答“依据哪里”，不能用模型推测的原因替代。
- 理由记录回答“为什么这样选”，明显且可查的内容不重复抄。
- 实质变更原因记录一次即可，关联到多个条目。
- 同一案例可以约束多条规则；案例的作用是验证，不自动形成新义务。
- 单条小改不需要完整 ADR、额外 JSON 主库或固定多 Agent 审核。
- 对关系尚未梳理的旧文档，审阅范围不能声称已完全收窄；先呈现已知关联与待核查项。

## 对新建 Agent

以“需求 → 可选设计与理由 → 建议职责／边界／输入输出 → 场景”呈现。不要假装已经有已批准规则，也不要只交规则清单而不回答设计是否可行。
